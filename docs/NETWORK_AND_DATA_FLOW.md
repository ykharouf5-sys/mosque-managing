# تقرير آلية البيانات والشبكة

تاريخ المراجعة: 2026-08-28

يغطي هذا التقرير تطبيق Flutter في `aqua orginal` وخادم Laravel في `backend` بعد مراجعة عنق الزجاجة والطلبات المكررة وتدفق الحسابات والمزامنة.

## النتيجة التنفيذية

- المستخدم العادي (`student`) يحصل بعد توثيق البريد على عيادة شخصية تلقائياً، ولا يمر بانتظار موافقة مدير ولا ببوابة إجبارية لإكمال الملف.
- لكل حساب ملف SQLCipher مستقل باسم `aqua_account_<account-id>.db` ومفتاح تشفير مستقل محفوظ في Secure Storage.
- تسجيل الخروج يغلق قاعدة الحساب ولا يحذف الملف أو المفتاح. حذف الحساب الصريح فقط يحذف البيانات المحلية الخاصة به.
- العودة بالحساب نفسه تعيد فتح الملف نفسه، ثم تكمل المزامنة التزايدية من الخادم.
- الخادم يعزل البيانات السريرية بالـ`clinic_id` وبنطاق المستخدم/الصلاحيات، ويربط مؤشر المزامنة بالمستخدم والعيادة وإصدار النطاق.

## تدفق بدء الجلسة

1. التسجيل يتم عبر REST ثم يرسل الخادم رمز OTP للبريد.
2. عند نجاح التحقق، ينشئ الخادم عيادة شخصية بمعرّف ثابت يساوي معرّف المستخدم. العملية محمية بمعاملة وقفل حتى لا ينشئ طلبان متزامنان عيادتين.
3. التطبيق يفعّل قاعدة SQLCipher الخاصة بمعرّف الحساب.
4. تحميل أو مزامنة البيانات يبدأ مرة واحدة للجلسة. تحديث الاسم أو الصورة لا يعيد تهيئة كل مزودي البيانات.
5. تحميل المتجر، المزامنة السريرية، إعادة محاولة الطلبات المعلقة، وربط البيانات الأكاديمية يعمل بالتوازي عند الحاجة.

عند تسجيل الخروج يغلق التطبيق اتصال SQLite ويلغي المؤقتات والـlisteners ويربط الواجهات بحالة فارغة، لكنه يحتفظ بملف الحساب المشفر. الكاش العام للكتالوج لا يُحذف عند تبديل الحساب لأنه لا يحتوي بيانات مستخدم خاصة.

## أين يُستخدم REST API؟

جميع مسارات الخادم تحت `/api/v1` وتعمل عبر HTTPS في نسخة الإنتاج. المصادقة تستخدم Laravel Sanctum، والمسارات المحمية تمر عبر `auth:sanctum` و`verified` وقيود السرعة والصلاحيات.

| المجال | أهم المسارات | الاستخدام |
|---|---|---|
| المصادقة | `POST auth/register`, `POST auth/login`, `POST auth/otp/send`, `POST auth/otp/verify`, `GET auth/me`, `PUT auth/profile`, `POST auth/logout` | إنشاء الجلسة والتحقق والملف الشخصي |
| المزامنة السريرية | `POST sync/push`, `GET sync/pull` | رفع طابور التغييرات المحلية وسحب الفروقات |
| المرضى والمواعيد | `GET/POST/PUT/DELETE patients`, `GET/POST/PUT/DELETE appointments` | REST مباشر متاح، مع اعتماد التطبيق أساساً على local-first والمزامنة |
| المتجر | `GET store/catalog`, `GET store/products`, favorites, reviews, coupons | كتالوج ومنتجات وتفاعل المستخدم |
| الطلبات | `GET/POST orders`, `PATCH orders/{id}/status` | شراء المستخدم وإدارة الطلبات |
| الأكاديمي | subjects, enrollments, results, result-uploads | المواد والتسجيل والنتائج والرفع |
| الملفات والإشعارات | images, avatar, FCM token, notification-campaigns | رفع الوسائط وتسجيل الجهاز والإشعارات |

## المزامنة السريرية: Local-first

الكتابة على مريض أو موعد تحفظ أولاً في SQLCipher وتضاف إلى `sync_queue`. بعد debounce موحد مدته نحو 900ms يجمع التطبيق عمليات المرضى والمواعيد في طلب idempotent واحد إلى `POST /sync/push`. إذا احتوت الدفعة تعارضاً، يعود التطبيق إلى إرسال العناصر منفردة كي لا يمنع عنصر متعارض بقية العناصر الصحيحة.

بعد الرفع يسحب التطبيق التغييرات من `GET /sync/pull` باستخدام:

- `since`: آخر وقت خادم مكتمل.
- `cursor`: مؤشر موقع موقّع من الخادم ومرتبط بالمستخدم والعيادة وإصدار النطاق.
- `limit=25`: حد أقصى ثابت لكل نوع في الصفحة.
- snapshot time: يمنع تغيّر حدود الصفحة أثناء دورة السحب.

الخادم يقرأ `limit + 1` داخلياً ليعرف إن كانت هناك صفحة أخرى فعلاً، ثم يعيد 25 فقط. لذلك العدد المطابق تماماً لحجم الصفحة لا يسبب طلب صفحة فارغة.

المزامنة الآن single-flight: أي شاشتين تطلبان المزامنة في اللحظة نفسها تنتظران العملية نفسها. المزامنة الدورية كل 5 دقائق وفي foreground فقط، مع حد أدنى 15 ثانية بين التشغيلات التلقائية. الرجوع من انقطاع الشبكة له listener واحد فقط، والطلبات التي تتولد من عدة كتابات قريبة تتجمع في مؤقت واحد.

## أين توجد Pagination؟

| البيانات | النوع | الحجم الافتراضي/الأقصى |
|---|---|---|
| دليل المرضى في Flutter | SQLite `LIMIT/OFFSET` | 25 |
| مزامنة المرضى والمواعيد | cursor pagination | 25 لكل نوع |
| REST المرضى | page pagination | 25 كحد أقصى |
| REST المواعيد | page pagination | 25 كحد أقصى |
| منتجات المتجر | page pagination | 20 افتراضي، 25 كحد أقصى؛ التطبيق يطلب 25 |
| الطلبات | page pagination | 20 افتراضي، 25 كحد أقصى؛ التطبيق يطلب 20 |
| المراجعات | page pagination | 20 افتراضي، 50 كحد أقصى |
| الدفعات | page pagination | 25 |
| الكوبونات | page pagination | 25 افتراضي، 50 كحد أقصى |
| ملفات النتائج | page pagination | 20 افتراضي، 50 كحد أقصى |

شاشة دليل المرضى تقرأ 25 صفاً فقط من SQLite ثم تستخدم `OFFSET` عند الاقتراب من نهاية القائمة. أما لوحات الإحصاءات والتقارير فتحتفظ بالمجموعة المحلية الكاملة عمداً لأن حساب الإجماليات على صفحة واحدة يعطي أرقاماً خاطئة.

## المشاكل التي أزيلت

- أزيل listener مكرر كان يشغّل المزامنة مرتين عند عودة الإنترنت.
- أزيل تكرار طلب المنتجات داخل `store/catalog`؛ الكتالوج يعيد الفئات والبنرات فقط عبر `include_products=0`، والمنتجات تأتي من endpoint الـpagination وحده.
- أضيف single-flight لطلبات الكتالوج والطلبات والمزامنة، ومنع بدء تحميل أولي ثانٍ أثناء الأول.
- صُحح حجم صفحة المنتجات من 30 إلى 25 ليتطابق مع حد الخادم؛ عدم التطابق كان يوقف التحميل بعد أول 25 منتجاً.
- تحديث الصورة أو الملف الشخصي لم يعد يعيد فتح قاعدة البيانات أو يعيد تحميل كل التطبيق.
- الاستجابة الفارغة للمواد الأكاديمية أصبحت حالة محمّلة صحيحة، فلا يعاد نفس طلبي subjects/enrollments مع كل شاشة.
- polling إدارة المتجر أصبح كل دقيقتين وفي foreground فقط، ويحفظ cursor الوقت حتى عندما لا توجد تغييرات.
- تسجيل FCM token أصبح single-flight ولا يكرر POST عندما يعيد Firebase الرمز نفسه.
- صور المتجر تستخدم كاش ذاكرة وقرص بدلاً من إعادة تنزيلها عند كل بناء للواجهة.
- إعادة المحاولة التلقائية بقيت لطلبات GET. عمليات POST/PUT/PATCH/DELETE لا تعاد افتراضياً لتجنب تكرار الكتابة، وتفعل retry فقط عندما يكون الطلب idempotent صراحة.
- backoff للطلبات لا يحتجز خانة من حد التزامن أثناء الانتظار.
- أضيف التحميل الأولي الناقص لشاشة طلباتي.

## الكاش والـpolling

- خادم الكتالوج يستخدم versioned cache وETag، مع مفتاح منفصل للنسخة الكاملة والنسخة المختصرة.
- Flutter يحتفظ بالكتالوج العام بين الحسابات، بينما يمسح مزودي المرضى والمواعيد والطلبات عند تبديل الحساب.
- المراجعات مخزنة خمس دقائق لكل منتج.
- polling ليس بديلاً عن المزامنة السريرية؛ يستخدم فقط لتحديث تغييرات الإدارة في المتجر والطلبات عندما يكون التطبيق مفتوحاً.

## سياسة الفشل

- GET: إعادة محاولة محدودة للأخطاء العابرة مثل 429 و5xx.
- عمليات الكتابة: بلا retry افتراضي، إلا مع idempotency key أو batch sync الآمن.
- 4xx الخاصة بالتحقق لا تعاد.
- طابور الطلبات يعيد جدولة المحاولة بعد backoff من دون استهلاك slot اتصال.
- فشل عنصر واحد في batch sync لا يلغي محاولة بقية العناصر؛ يستخدم fallback فردياً.
